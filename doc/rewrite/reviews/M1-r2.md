# Review M1, round 2: port of miniQU to the new architecture

Reviewer verdict: **not approved**. One blocking item (B1): under the
benchmark protocol the new binary is 12-27% slower than the baseline on
identical searches of the `DW` family, the round-2 gate of the ROADMAP on
families is not met, the benchmark report does not say so, and the cause is
not known. Everything else is accepted: the new layout, the code, soundness,
proofs, and parity in solved instances and PAR2.

Reviewed: branch `rewrite/cadical-style` at `0e68e7a`; solver sources as of
`60dce84` (no source change after it), binary sha256 `30bd8fe6b956`. My own
release build of HEAD is bit-identical to the benchmarked binary
(`/home/ec2-user/miniqu-work/review-M1-r2/release`, 0 warnings, ctest 38/38).
Read in full this round: the diff `edd1f12..HEAD` of `src/` and `test/`, and
`constraint.hpp`, `watch.hpp`, `collect.cpp`, `reduce.cpp`, `solver.cpp`,
`learn.cpp`, `propagate.hpp`, `propagate.cpp`, and the three files round 1
had only sampled: `analyze_ldq.cpp`, `propagate_ldq.cpp`, `minimize.cpp`.

## 1. Architecture and owner constraints: accepted

- **Arena** retained. The layout is now MiniSat's: one header word, the
  literals, a trailing glue word only for redundant constraints, two trailing
  id words only while a tracer is connected. Only `constraint.hpp` knows it.
- **Watch lists** retained: 8-byte `Watch{Ref, blocker}`, one list per
  literal and kind, lazy cleaning, collection in watch order. Round 2 put
  both lists and the dirty flags of a literal into one 64-byte record and
  uses MiniSat's 3/2 growth; both are inside the owner's constraint.
- The id-less layout is consistent: tracers can only be connected before the
  first original (`REQUIRE` in `Solver::connect_tracer`), every id read is
  under `if (proof)` or `has_id ()`, `check_invariants` checks
  `has_id == (proof != nullptr)` for every listed constraint, and
  `reduce` no longer reads ids (stable sort over creation order).
- `size_watches` is safe: `add_var` is rejected after the first original, so
  the records are never too short.
- BVE side conditions: not applicable to M1.

## 2. Soundness and proofs: accepted

- `shrink` moves the trailing words down before the size changes (forward
  copy, destination below source); `set_size` of the model buffer saves the
  id, and `initial_cube` now sets the size before copying the literals, which
  is the order the trailing id needs. `copy_constraint` is a verbatim copy
  and asserts that the source is neither garbage, moved nor protected;
  `reduce` unprotects before it collects.
- Mode 2 (`analyze_ldq`, `propagate_ldq`), read in full this time: opposite
  literals of a secondary variable can only meet when both are unassigned
  and right of the pivot (a reason holds unassigned secondary literals only
  right of its forced literal), which is the side condition of long-distance
  resolution. No proof exists for this mode and none is claimed; the tracer
  is rejected at start-up.
- Minimisation: in modes 0 and 1 a reason is fully assigned, so no
  complementary pair can arise; it stays off while a tracer is connected,
  with a warning. Not silently disabled.
- Own proof checks with the Lean checker on benchmark instances, new layout
  with ids: **7 of 7 `s VERIFIED`** with the right verdict:
  `DW-sat-08-22-1`, `lift_gr1+2.tlsf` (`--seed=2`), `hadw10-11` (`-dl`,
  116 MB), `collector_v17.tlsf` (`-mode=1`),
  `chess_solving_mate_in_2_1982_WCSC-6_02` (`-mode=1 -dl`), and two with
  reductions and collections, so with relocated ids: `jctc2-pass`
  (`--reduceint=50 --tier1glue=0 --gcfrac=0`, 9 collections) and
  `DW-unsat-09-22-1` (`--reduceint=200 --tier1glue=0 --gcfrac=0`, 8
  collections). An eighth run (`jctc10-fail`, mode 1) did not finish solving
  in 300 s with a proof and was not checked.
- Own fuzz on seeds nobody had used:
  `tests/regress.sh -S -j 16 -s 7001:7080 -M all` on the release binary:
  "REGRESSION TESTS PASSED (5 warnings)", all warnings solver timeouts
  (mode1-dl 2, mode2-dl 1, noearly 7, restart-dl 2, restart-mode1-dl 3), no
  wrong verdict, no rejected proof.
- The independent verification (matrix 1:300 release, QDIMACS, asan) is
  clean. The asan gate at `-t 240` follows the owner decision on sanitizer
  timeouts and decision E3.

## 3. Code quality: accepted

The round-2 changes are small and readable; the layout comment in

## 4. Performance evidence

### 4.1 What is convincing

- **Verdicts**: no discrepancy over all runs in `bench/results/` (my own
  scan), and none in my four extra runs. `2.1` and `5.2-3` hit the 8 GB
  limit in every run of both binaries; the report's "no MEMOUT problems"
  should say that.
- **Solved and PAR2**: within seed noise in all five configurations, as the
  report says. The claims match the CSVs.
- **No time-of-day bias**: the baseline runs are 12 hours older than the
  round-2 runs. I reran default and mode 1, seed 1, both binaries back to
  back on the idle machine (`/home/ec2-user/miniqu-work/review-M1-r2/res/`).
  The same binary on the same search differs between the committed run and
  mine by a geometric mean of 1.000 (new, n=101) and 1.014 (baseline,
  n=100), standard deviation of the log ratio 0.075 per instance. Solved:
  baseline 141, new 140 (default); 114 and 115 (mode 1).
- **Memory**: peak RSS about 0.80-0.95 of the baseline on instances above
  64 MB. Decision E1 on `1.3` is sound.
- **Pooled engine speed** on identical searches: default 1.027 / 1.042 /
  1.007 (my rerun 0.999), `-dl` 1.007 / 0.990 / 0.995, mode 2 0.975. That
  part of the gate ("about 1.03") is met. Mode 1 is 1.063 (my rerun 1.062).

### 4.2 B1 (blocking): the family gate fails and nobody says so

The ROADMAP gate of this round reads: geometric mean at most about 1.03 in
default and `-dl`, **no family of three or more instances above 1.10**. The
committed paired reports mark, on identical searches:

| config | family | n | new / baseline |
|---|---|---:|---:|
| default | DW | 6 | 1.144 |
| default | hadw | 3 | 1.133 |
| `-dl` | DW | 4 | 1.107 |
| mode 1 | DW | 5 | 1.260 |
| mode 1 | chess | 11 | 1.119 |

`M1-r2-report.md` does not mention the family criterion; it writes "within a
few percent" and "Blocking items: none". STATUS lists the benchmark-set gate
as "open: measured in the benchmark stage" and it was never closed.

It is not noise. My back-to-back reruns give DW 1.163 (default, n=6) and
1.268 (mode 1, n=5), chess 1.172 in mode 1 (n=11); `hadw` in default did not
repeat (0.921) and is noise. With 0.075 per instance, a family of six is
resolved to about 0.04. The parse-dominated `numeric` family (0.93-0.96)
hides the rest in the pooled number: without it the search-dominated
instances are about 1.03-1.07 in default and 1.13 in mode 1.

It contradicts the load gate. `bench/load_measure.py` reports 0.827
(default) and 0.818 (mode 1) with `DW` at 0.59-0.81, and STATUS concludes
"gate met". On `DW-sat-08-22-1`, seed 1, same search: 1.96 s -> 1.58 s there,
2.0 s -> 3.0 s in three benchmark runs. Two instruments, opposite signs, and
the one that is the protocol says slower.

**Reproduction in two minutes** (user CPU time, machine otherwise idle).
`run.py` starts the instances in name order, one per core, so the eight
cores 80-87 of one L3 cache run `CM-unsat-07-01-06-2` and the seven `DW-*`
instances together. The same eight on cores 0-7, one binary at a time, 40 s
limit, two rounds (`/home/ec2-user/miniqu-work/review-M1-r2/l3.sh OUT 0 ""`):

| instance | baseline s | new s | ratio |
|---|---:|---:|---:|
| DW-sat-08-22-1 | 2.40 | 2.98 | 1.24 |
| DW-sat-08-23-1 | 1.66 | 2.59 | 1.56 |
| DW-sat-09-26-1 | 3.14 | 3.44 | 1.10 |
| DW-unsat-09-22-1 | 8.32 | 11.93 | 1.43 |
| DW-unsat-09-23-1 | 17.77 | 19.55 | 1.10 |
| DW-unsat-10-25-1 | 25.42 | 29.30 | 1.15 |
| geometric mean | | | 1.25 |

The two rounds agree within 3% on every instance but one.

**What I found about the cause** (not a diagnosis):

1. It is what the new binary does to its cache neighbours, not how it runs
   itself. Target on one core, the other seven of the group on the same L3
   (`cross.sh`):

   | target | neighbours baseline | neighbours new |
   |---|---:|---:|
   | DW-unsat-09-22-1, baseline | 15.8, 13.1 | 17.6, 17.5 |
   | DW-unsat-09-22-1, new | 15.9, 13.9 | 18.8, 18.6 |
   | DW-sat-08-23-1, baseline | 1.52, 1.54 | 2.31, 2.37 |
   | DW-sat-08-23-1, new | 1.63, 1.65 | 2.53, 2.50 |

2. It is steady search, not start-up. Seven copies of `DW-unsat-11-26-1`
   warmed up for 12 s, then the baseline binary on `DW-sat-08-23-1`
   (`nb.sh`): baseline neighbours 1.41-1.46 s, new neighbours 2.16-2.22 s
   (six of six).
3. With `alignas (64)` removed from `Watches::PerLit` (nothing else changed)
   the neighbours of experiment 2 are harmless (1.35-1.59 s, six runs), but
   the eight-instance table above is still at 1.20. So the aligned record is
   part of it and not all of it.
4. The round-1 binary as neighbour is bimodal (1.46-1.54 four times, 2.24
   and 2.98 once each), which smells of memory placement.
5. `load_measure.py` cannot see this: it puts copy k of instance j on core
   `k * 12 + j`, so an L3 group is a mix of instances, and a core stays idle
   once its instance is solved. In a benchmark run the group is one family
   and the cores are refilled.

**Why this blocks.** The coordinator's gate for this round is not met and no
decision accepts the excess. A 25% slowdown in a two-minute reproducer is
significant, and it is unexplained. The report's claim does not match its own
paired tables. The effect sits in the watch and arena footprint that M2
builds on, and from M2 on every comparison is new against new, where it can
no longer be seen.

**B1, to do:**

1. Find what makes the new binary a heavier cache neighbour on the `DW`
   group, with `l3.sh`, `cross.sh` and `nb.sh` in
   `/home/ec2-user/miniqu-work/review-M1-r2/` (copy them into `bench/` if
   they are kept). Fix it, or show by measurement what it costs and record a
   coordinator or owner decision in STATUS.md that accepts it.
2. Make the load instrument predict the protocol: neighbours placed as
   `run.py` places them (name order within an L3 group) and cores kept busy
   for the whole measurement, or replace it by a `run.py` slice of the first
   48 instances run for both binaries in alternation. Until then
   `load_measure.py` results are not evidence about benchmark runs.
3. The benchmark report evaluates the ROADMAP gate line by line, including
   the per-family table of every configuration.
4. Gate for round 3, inside the normal budget: the `l3.sh` table has a
   geometric mean of at most about 1.05, and in the benchmark stage no
   family of three or more instances is above 1.10 on identical searches in
   default and `-dl` (mode 1: reported, and explained if above), or the
   excess is accepted by a recorded decision as in step 1.

## 5. What the reduced evidence can and cannot show

- Verdicts: 27 committed runs plus my four without a discrepancy, the matrix
  fuzz and my 80 fresh seeds. Strong.
- Proofs: fuzz matrix with Lean checking, the 33 smoke proofs, my seven
  benchmark proofs. No proof-coverage run on the benchmark set exists for
  this binary (budget); coverage against the baseline's table is unmeasured.
- Speed: three seeds at 60 s cannot resolve one or two solved instances.
  Identical searches resolve engine speed to about 1-2% pooled and 4% for a
  family of six, which is what B1 rests on.
- Mode 1, mode 2 and ccmin3 have one seed each; the ccmin3 identical-search
  number rests on four instances and says nothing.

## 6. Suggestions (not blocking)

- `Watches::PerLit::dirty` relies on value-initialisation by `resize`; write
  `dirty{}`.
- `Watches::init`, `Internal::shrink_constraint` and `Proof::strengthen` have
  no caller outside the unit tests yet. Keep them only if M2 uses them.
- `redundant` now decides the size of a constraint (`words ()`), so it can
  no longer be cleared in place. ARCH 5.2 should say that promoting a learnt
  constraint to irredundant (subsumption, BVE in M3) means a reallocation.
- State the mode-1 pooled ratio (1.06) as a known deficit in STATUS if it
  survives B1; the round-2 gate for mode 1 was only the sign test, which it
  passes (18 wins, 21 losses).
